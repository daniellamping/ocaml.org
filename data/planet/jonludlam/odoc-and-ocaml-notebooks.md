<h1><a href="https://jon.recoil.org/atom.xml#odoc-and-ocaml-notebooks" class="anchor"></a>Odoc and OCaml Notebooks</h1>
<ul class="at-tags"><li class="published"><span class="at-tag">published</span> <p>2026-04-06</p></li></ul>
<ul class="at-tags"><li class="page-tags"><span class="at-tag">page-tags</span> <p><a href="https://jon.recoil.org/tags/odoc.html" title="odoc">odoc</a> <a href="https://jon.recoil.org/tags/notebooks.html" title="notebooks">notebooks</a> <a href="https://jon.recoil.org/tags/tessera.html" title="tessera">tessera</a></p></li></ul>
<p>As the chief maintainer of OCaml's odoc, I'm required to think hard about its future. What impact will advances in <a href="https://anil.recoil.org/notes/aoah-2025">agentic programming</a>, <a href="https://dl.acm.org/doi/10.1145/3759536.3763802">collaborative literate coding</a>, and the dramatic increase in web platform capabilities through <a href="https://ocaml.org/tools/wasm-target">wasm</a> and WebGPU have — both on how odoc works and on how we develop it?</p>
<p>I find the best way to explore these topics is to <i>build</i> something, so I've gone all-in on Claude and used it to rewrite my website with all new odoc-built dune-friendly client-side Jupyter-style notebooks as an integral part of it! Those of you that have read this blog for a while will know I've been <a href="https://jon.recoil.org/2025/07/retrospective.html" title="retrospective">tinkering with notebooks</a> for a year or so now, and I've had an <i>extremely</i> long-running fascination with <a href="https://jon.recoil.org/2025/12/an-svg-is-all-you-need.html" title="an-svg-is-all-you-need">scientific visualisation in the browser</a>, but I really wanted to push this hard and see how adding Claude into the mix would work out.</p>

<figure>
  <a href="https://jon.recoil.org/notebooks/interactive_map.html"><img src="https://jon.recoil.org/notebook.png" alt="A client-side notebook using TESSERA"></a>
  <figcaption><em>A client-side notebook using TESSERA</em></figcaption>
</figure>

<p>It's very helpful to have a specific use-case in mind for the notebooks to guide the exploratory work. This was an easy choice: My group has been spending a lot of time recently on <a href="https://geotessera.org/">TESSERA</a>, and this provided a perfect demonstration for the notebooks, as it heavily relies upon being able to use interactive maps to choose areas of interest, and to visualise the embeddings and picture the output as map overlays. As well as being a fine motivating example, it's also given me an excellent reason to learn more about geospatial coding, which I've been wanting to do for a while. The <a href="https://github.com/ucam-eo/tessera-interactive-map">specific example</a> I chose to port required adding support for various interactive widgets in the browser-based programming environment, where I'd only previously been able to render <a href="https://jon.recoil.org/2025/04/this-site.html" title="this-site">static rich content</a>.</p>
<p>Also, inspired by my colleagues' <a href="https://digitalflapjack.com/blog/marimo/">experiences with notebooks</a>, I've been <a href="https://jon.recoil.org/atom.xml#execmodel" title="execmodel">experimenting with the execution model</a> and interactivity to ensure reproducibility, and considering the implications of the FAIR (findability, accessibility, interoperability, reusability) principles of the <a href="https://dl.acm.org/doi/10.1145/3759536.3763802">Fairground paper</a>, which provides a perfect framework of requirements for the odoc notebooks. These more ambitious goals meant a more ambitious approach to the changes.</p>
<p>Despite this, with this rewrite I've thought much harder to ensure that what I've done will fit into the upstream ecosystem. It's now all built using dune with the standard rules I've <a href="https://jon.recoil.org/2025/12/claude-and-dune.html" title="claude-and-dune">already started upstreaming</a>, and by using plugins with odoc I've minimised the necessary changes to the core of odoc. While there's work to be done, there's a far clearer path to ensuring this work can be used by everyone.</p>
<p>I've chosen to use OxCaml both for the build environment and the runtime environment on the web. While the choice doesn't make a huge difference in the browser, a longer-term vision is to have a choice of execution environments, and oxcaml for running high-performance numerical code makes a lot of sense.</p>
<p>The implementation work can roughly be split into three parts: <a href="https://jon.recoil.org/atom.xml#infrastructure-and-odoc" title="infrastructure-and-odoc">Infrastructure and Odoc</a>, the <a href="https://jon.recoil.org/atom.xml#x-ocaml-and-js_top_worker" title="x-ocaml-and-js_top_worker">Js_top_worker and widgets</a> libraries, and the actual <a href="https://jon.recoil.org/atom.xml#tessera-notebooks" title="tessera-notebooks">TESSERA code</a>. Then I've got some thoughts on the <a href="https://jon.recoil.org/atom.xml#implications" title="implications">implications</a> of the experience, for open source development in general and odoc and the notebooks specifically.</p>
<h2><a href="https://jon.recoil.org/atom.xml#infrastructure-and-odoc" class="anchor"></a>Infrastructure and Odoc</h2>
<p>In order to have a fast build cycle I needed an incremental build. Last year I wrote up my experiences writing the <a href="https://jon.recoil.org/2025/12/claude-and-dune.html" title="claude-and-dune">dune rules for odoc</a> with Claude. I opened <a href="https://github.com/ocaml/dune/pull/12995">the PR</a>, representing a "feature complete" replacement for the current rules, in that it can completely replace what's in dune now, but doesn't extend the rules for the new features of odoc. Since then we've merged the first part of it, and happily my colleague <a href="https://choum.net/panglesd">Paul-Elliot</a> is back from his brief sabbatical working on <a href="https://docs.slipshow.org/en/stable/">slipshow</a> to work on getting the rest of it merged.</p>

<figure>
  <img src="https://jon.recoil.org/fix-doc-bugs-with-dune.gif">
  <figcaption><em>The incremental build, together with "--warn-error" is very helpful when fixing documentation bugs!</em></figcaption>
</figure>

<p>To support my goals though, I've had to extend the rules by quite a lot from that initial work. I've got <a href="https://github.com/ocaml/dune/commit/0aa0170938b92342a609476abab67b960c356bd5">support for assets</a> so I can put images on my blog posts, support for <a href="https://github.com/ocaml/dune/commit/91b08307c118193fc46a707891c28721c1778916">source rendering</a> so that you can see the code I'm using. There's <a href="https://github.com/ocaml/dune/commit/4cb2b33e98634eba8b9a267a6dd9bcfc959575a4">markdown output</a> for Claude to consume, and <a href="https://github.com/ocaml/dune/commit/76f61319a21ba8b03feeb0c15e2a567ca2114489">sherlodoc native support</a> so you (or your agent) can run sherlodoc queries on the command line. The <a href="https://github.com/ocaml/dune/commit/91b08307c118193fc46a707891c28721c1778916">prefix</a> for all output is configurable, so that I was able to put everything dune built under "/reference", and pass <a href="https://github.com/ocaml/dune/commit/48a5cbb79b24606304dc25f965c22aa5e4cb898e">arbitrary options</a> to the various invocations of odoc so that I could specify global defaults like the Javascript toplevel worker and opam repository to use in my notebooks. We've also now got <a href="https://github.com/ocaml/dune/commit/a49e98a88d7358074afffedfb0f6ee922208cdb7">smarter rules</a> that don't pull in as many dependencies as the current PR, so that I didn't have to install any extra packages I wasn't using just to build my own docs.</p>

<figure>
  <img src="https://jon.recoil.org/sherlodoc-search.png">
  <figcaption><em>Sherlodoc database generation and search using dune. Note that the output is rendered with markdown!</em></figcaption>
</figure>

<p>Most of these changes will be useful to the wider OCaml community, so it makes sense to try to upstream them. They're also fairly orthogonal to each other, and are obviously dependent on the original PR, and hence they can be made as independent PRs once the big one has been merged.</p>
<h3><a href="https://jon.recoil.org/atom.xml#odoc" class="anchor"></a>Odoc</h3>
<p>OxCaml support for odoc was contributed by Luke Maurer early on after OxCaml was released. However, this only fixed the build of odoc, it didn't give it any mode or layouts, nor any of the other new features of OxCaml. I asked Claude to look through the way the toplevel prints these annotations and port them to odoc, and that's been implemented on this site. For example, see <a href="https://jon.recoil.org/reference/base/base/Base/Uniform_array/index.html#val-length"><code>Base.Uniform_array.length</code></a> - you can see there the <code>portable</code>, <code>local</code> and <code>contended</code> annotations on the type. If you click on the <code>source</code> link, you'll see I also added some improvements to the source rendering - there are many more links now and we've got the ability to link to source from doc comments and mlds.</p>

<figure>
  <a href="https://jon.recoil.org/reference/base/base/Base/Uniform_array/index.html#val-length"><img src="https://jon.recoil.org/length-with-oxcaml.png"></a>
  <figcaption><em>Output from odoc, showing the oxcaml extensions</em></figcaption>
</figure>

<p>One of the earliest things I did was to give Odoc a new plugin system that has been hugely enabling for building the new features. I'm using dune's <a href="https://dune.readthedocs.io/en/stable/sites.html#sites">site</a> feature for the plugins, which really "just worked". It was very easy both to add the feature to odoc and to create the plugins themselves. Building a whole variety of plugins has also been very useful in testing the shape of the plugin API, and I've made numerous changes to it as I've built them and they expose various problems.</p>
<p>The plugins are activiated in a few different ways. The first is to allow <a href="https://ocaml.org/manual/5.4/ocamldoc.html#sss:ocamldoc-custom-tags">custom tags</a>, e.g. <code>@foobar &lt;content&gt;</code>, a feature of ocamldoc that odoc didn't previously support. The plugin registers handlers for a particular set of tags, and when odoc encounters that tag it calls the plugin to find out what should be rendered. The second way is for plugins to handle particular source-code blocks, e.g. <code>{@baz k1=v1 k2=v2[ ... ]}</code>. Once again when odoc encounters a matching block it gets passed to the plugin to determine what should be rendered.</p>
<p>Let's take a brief look through the plugins I've made.</p>

<h4><a href="https://jon.recoil.org/atom.xml#interactive-pages-(notebooks)" class="anchor"></a>Interactive pages (notebooks)</h4>
<p>My previous efforts at creating notebooks involved a separate pipeline to build them, but with this plugin it became trivial to have them built as part of the normal 'dune build' process.</p>
<p>The <a href="https://jon.recoil.org/reference/odoc-interactive-extension/index.html" title="index">odoc-interactive-extension</a> uses <a href="https://github.com/art-w">art-w</a>'s <a href="https://github.com/art-w/x-ocaml">x-ocaml</a> to add interactivity to the mld files. The plugin itself is rather simple, really just finding marked ocaml code blocks and outputting an <code>&lt;x-ocaml&gt;</code> element into the HTML. The metadata in the code block is translated directly into attributes in the x-ocaml tag allowing arbitrary parameters to be passed.</p>
<p>I have some more detail on x-ocaml and js_top_worker <a href="https://jon.recoil.org/atom.xml#x-ocaml-and-js_top_worker" title="x-ocaml-and-js_top_worker">later in this post</a>.</p>

<h4><a href="https://jon.recoil.org/atom.xml#html-shells" class="anchor"></a>HTML shells</h4>
<p>The "traditional" way that you embed odoc output into another webpage, like ocaml.org does, is to output JSON. This works well where you've got a smart server that can read the JSON and render it on demand, but when you're trying to build a static website like the dune rules produce, it's rather less convenient.</p>
<p>The HTML shells extension is part of the odoc plugin system, and allows you to swap out the default HTML renderer for another completely customisable one. I have two plugins that use this system:</p>
<ul><li><a href="https://jon.recoil.org/reference/odoc-docsite/index.html" title="index">odoc-docsite</a> which produces a more modern SPA-style site.</li><li><a href="https://jon.recoil.org/reference/odoc-jons-plugins/index.html" title="index">jons-shell</a> which produces this website.</li></ul>
<p>The advantage of using these is that it doesn't affect the flow of the documentation pipeline, so there are no changes required to the dune rules for it to produce a very different output. You just install the plugin, add the '--shell &lt;...&gt;' to the dune file or dune-workspace file at the root of your repository, and run <code>dune build @doc</code>.</p>
<p>The second of these plugins is a good example of a bit more of an involved one - see the <a href="https://tangled.org/jon.recoil.org/odoc-jons-plugins">source code</a>.</p>
<h2><a href="https://jon.recoil.org/atom.xml#x-ocaml-and-js_top_worker" class="anchor"></a>X-OCaml and Js_top_worker</h2>
<p><a href="https://github.com/art-w/x-ocaml">x-ocaml</a> is <a href="https://github.com/art-w">art-w</a>'s excellent tool to to add interactivity to any web page. It works by registering a new HTML element <code>x-ocaml</code> that can be used like any normal HTML element, producing a Codemirror-backed editor with a "run" button that will execute your code in your browser using a web worker.</p>
<p>In order to use OxCaml in my notebooks, I needed a stronger separation between the code running in the browser context and the "execution engine" running in the web worker. I switched from <a href="https://jon.recoil.org/reference/ocaml-variants/stdlib/Stdlib/Marshal/index.html"><code>Marshal</code></a> for the communications layer to <a href="https://jon.recoil.org/reference/js_top_worker-client/js_top_worker-client.msg/Js_top_worker_client_msg/index.html" title="Js_top_worker_client_msg">JSON</a>, as marshal is incompatible between OxCaml and OCaml, which meant that a single frontend implementation can now talk to both OxCaml and OCaml workers running in the web worker.</p>
<p>My fork is using <a href="https://github.com/jonludlam/js_top_worker">js_top_worker</a> as the library and tool that's used to manage the javascript toplevels. The goal of the tool is to use it to have toplevels or interactive notebooks for every package in opam-repostiory, so it's important that it's careful about what can be cached. As such, the design is that there's a single toplevel worker, and libraries can be dynamically loaded in via <code>#require</code>, just like the standard toplevel. Each library is compile from a <code>cma</code> to a <code>cma.js</code>, and the <code>cmi</code>s are also dynamically fetched as they're needed. The worker, the <code>cma.js</code> files and <code>cmi</code>s are then hosted alongside <code>META</code> files and an index.</p>
<p>The <a href="https://jon.recoil.org/_opam/findlib_index.json">Toplevel index file</a>:</p>
<div><pre class="language-json"><code>{"meta_files":
  [ "lib/yojson/META",
    "lib/uutf/META",
    "lib/uri/META",
    ...
    "lib/js_top_worker-rpc/META"
    ],
 "compiler":
   {"worker_url": "worker.js"}
}</code></pre></div>
<p>One important new feature of js_top_worker that I've built for the notebooks is the ability to use interactive widgets. This requires two-way communications between the main javascript thread and the web-worker backend as we want to be able to trigger changes from both sides. Rather than hard-coding all the widgets that can be made, the design allows new ones using standard OCaml libraries, so you can dynamically load in the widgets you require into your notebook, or even write new widgets there directly.</p>
<p>Each widget either has direct DOM callbacks, or injects some javascript glue code into the frontend, which then communicates between back and frontend using JSON. This layer is mostly "stringly typed" using the <a href="https://jon.recoil.org/reference/js_top_worker-widget/js_top_worker-widget/Widget/index.html" title="Widget">widget library</a>. On top of that you can then build more strongly typed libraries like the <a href="https://jon.recoil.org/reference/js_top_worker-widget-leaflet/index.html" title="index">Leaflet library</a> that give a more pleasant interface. Communications happen in both directions, so code can cause widgets to change, and interaction with the widgets can cause code to execute.</p>

<figure>
  <a href="https://jon.recoil.org/reference/js_top_worker-widget-leaflet/index.html"><img src="https://jon.recoil.org/leaflet-fly.gif"></a>
  <figcaption><em>Click to fly, executing via OCaml</em></figcaption>
</figure>

<p>Try the demo out yourself <a href="https://jon.recoil.org/reference/js_top_worker-widget-leaflet/index.html" title="index">here</a>.</p>
<h3><a href="https://jon.recoil.org/atom.xml#execmodel" class="anchor"></a>Execution model</h3>
<p>My colleague Michael Dales <a href="https://digitalflapjack.com/blog/marimo/">wrote about</a> the challenges of balancing interactivity and incremental computation in notebooks, and his post he settled on <a href="https://marimo.io/">Marimo</a>. The approach that Marimo takes is to analyse the code and build a dependency graph so that as values are adjusted, any affected part of the computation can be re-evaluated. You can then create values with UI elements attached, and the whole experience is very pleasant.</p>
<p>The "usual" approach to this sort of UI interaction in OCaml is to use an incremental library of some sort, like Jane Street's <a href="https://github.com/janestreet/bonsai/">Bonsai</a> or <a href="https://erratique.ch/software/react">React</a>. In this way we can build the dependency graph and re-evaluation semantics <i>within the language</i>. In these examples, I've used <a href="https://erratique.ch/software/note">Note</a>. The interesting wrinkle in this work is that because all interactions are being mediated by <code>js_top_worker</code>, we've got a single place where we could <i>record</i> the interactions that have happened, and then potentially "play them back".</p>
<p>With support for OxCaml, widgets and dynamic library loading, and integration into the docs pipeline via the odoc interactive plugin, it was time to create a real-world notebook to verify that it could be used to do "proper science"!</p>
<h2><a href="https://jon.recoil.org/atom.xml#tessera-notebooks" class="anchor"></a>TESSERA notebooks</h2>
<p>One of the most exciting things to come out of our group recently has been <a href="https://geotessera.org/">TESSERA</a>, a pixel-wise Earth observation foundation model. The code and demos for this are mostly in Python, particularly using Jupyter notebooks. This provided me with an excellent stress test that tied together many of the strands of this work and validated that they could be used together to build something useful. A <a href="https://github.com/ucam-eo/tessera-interactive-map">simple python notebook</a> showing the basic workflow already existed, so I decided to port it to OxCaml, and more specifically to make an odoc notebook. You can run the resulting <a href="https://jon.recoil.org/notebooks/interactive_map.html" title="interactive_map">OxCaml notebook</a> in your own browser, with no server required at all.</p>
<p>The notebook works by first presenting a map, and asking the user to select an area to download the TESSERA embeddings. Once we've got the 128-dimensional per-pixel values, we then need to display them. Rather than simply picking 3 dimensions as our RGB values, we do a PCA computation to choose some vectors for our colours. This is then overlaid on the map by first turning it into a <code>.png</code>, then encoding it as a base64 data URL, and passing it to the frontend to overlay on the map. The user then picks some points on the map, categorising them into arbitrary groups. We then run a knn classifier over the whole downloaded area and finally overlay that image.</p>
<p>I struggled a little with co-ordinate systems, mostly because the distortion if you <i>dont</i> map is fairly small, so it looks pretty good. However, you can see clearly on this image that the A14 (the red road at the bottom left) is a little bit off:</p>

<figure>
  <img src="https://jon.recoil.org/tessera.png">
  <figcaption><em>An earlier attempt, showing the distortion</em></figcaption>
</figure>

<p>In the newer notebook where I do the remapping correctly, it matches much better. You can see the remapping by looking at the left and right sides of the overlay, where they're no longer quite vertical.</p>

<figure>
  <a href="https://jon.recoil.org/notebooks/interactive_map.html"><img src="https://jon.recoil.org/notebook.png" alt="A client-side notebook using TESSERA"></a>
  <figcaption><em>Remapped overlay showing better matching with the map</em></figcaption>

<p>This version uses the <a href="https://jon.recoil.org/reference/tessera-npy/tessera-npy/Npy/index.html" title="Npy">Numpy</a> interface to TESSERA, which downloads the embeddings in quite large (100M) chunks. While it was nice that this worked, it meant it was quite slow to see anything actually happening. I then switched to using the <a href="https://jon.recoil.org/reference/zarr-v3/zarr-v3/Zarr_v3/index.html"><code>Zarr_v3</code></a> format, which is far more efficient, using range requests, compression and better encoding to reduce the bandwidth requirements. This version is <a href="https://jon.recoil.org/notebooks/interactive_map_zarr.html" title="interactive_map_zarr">here</a>.</p>
<p>This really demonstrated that the approaches I've made with the various different strands of work can all be knitted together in a very useful way, allowing us to bring the strong type system of OCaml together with the ubiquitous runtime of the browser, and using the power of WebGPU to run calculations that can help to change our world for the better.</p>
<h2><a href="https://jon.recoil.org/atom.xml#implications" class="anchor"></a>Implications</h2>
<p>I've written (or caused to be written) a lot of code for this project. It's all "open source" in that the code is available, though this is the very minimalist sense of the term. I've both modified other people's code, and written other things from scratch, and pushed everything publicly on the <a href="https://tangled.org/jon.recoil.org/monopam-myspace">repostiory</a>. It's been a fundamentally different experience than everything I've done in the past 25 years or so of OSS development.</p>
<p>Traditionally with open source software, most people never change the code. The vast majority of people take the code, run it, use it, and get on with their lives, grateful to varying degrees to the authors. A much smaller number of people will make changes to the code. This requires an enormous investment of effort, firstly in learning to code at all and then learning the specific codebase sufficiently well to make a change. A small subset of these people go to the additional effort of trying to upstream the code, and open a PR. At this point, the maintainers of the code now <i>also</i> need to put in a lot of effort to review what's been sent, and engage with the contributor to address any issues with the code. So it's hard work. Why do people bother?</p>
<p>This process is helpful to the contributor as maintaining patches on an open source project is not only work, but <i>unpredictable</i> work. Upstream changes can require you to have to fix your modifications at any time, and those fixes might be anywhere from trivial to completely impossible. Getting your patch upstreamed means that there's a much better chance that whatever it is that was fixed or improved remains that way without further effort.</p>
<p>On the part of the maintainer, the effort of reviewing and interacting with the contributor will hopefully both improve the code, but also effectively enlarge your workforce as the contributor learns more about the project. The more people who know about the project, the easier maintenance becomes.</p>
<p>LLMs have totally upset the balance of these motivations. From the contributor's perspective, the effort now required to maintain your own fork of a project is <i>much</i> smaller, as you don't need to learn the codebase anywhere near as deeply, and you don't have to worry anywhere near as much about maintaining your fork as upstream changes. So it's both easier for there to be code changes, and it's less rewarding to try and upstream them. From the perspective of the maintainer, there may be many more low quality pull requests, and in many cases there will be limited value in trying to cultivate new contributors as the LLMs can't learn directly from the feedback, and the humans guiding the LLMs will know much less about the project as they haven't needed to in order to make the PR.</p>
<p>Where these adjusted values will lead is very hard to predict. Empirically though, I find that I've made few PRs over the last few months, but I've amassed a lot of new repositories and forks of existing repos, and it's been very easy to slip into this mode of working. The effect on non-programmers hasn't begun to happen really, but there <i>will</i> be an effect and it <i>will</i> be profound. I'll know when that moment arrives when my artist-rather-than-scientist family members are using LLMs to alter code - which to them will just be the latest change in MacOS that's happened, but <i>I'll</i> know what's going on.</p>
<h2><a href="https://jon.recoil.org/atom.xml#attribution" class="anchor"></a>Attribution</h2>
<p>My early purely-agentic commits were all authored by me and co-authored by Claude. This is a lie. Morally, I found I couldn't carry on like this so I've switched now to having the commits authored by "Jon's Agent". My plan is to rewrite the author when I've gone through it line by line, and even then, I feel that Claude ought to be marked as Author and I should just be adding my "Reviewed-by" line onto it. In either case, for a pull request to be made the human in the loop has the responsibility to justify the changes, and therefore has to be totally familiar with both the changes and the code being changed. I'm not at all fundamentally opposed to having LLMs involved in the process of making changes to open source code, but in my experience so far, there's a huge amount of effort that needs to go into it even after you've got working code and tests. I've tested the waters with my <a href="https://github.com/ocaml/dune/pull/12995">dune PR</a>, and have merged a <a href="https://github.com/ocaml/odoc/pull/1402">simple bugfix or two</a> to odoc. Even these one-liners needed careful thought and attention before I felt I could make a PR though, and the dune PR took <a href="https://jon.recoil.org/2025/12/claude-and-dune.html" title="claude-and-dune">much more effort than that</a>.</p>
<h2><a href="https://jon.recoil.org/atom.xml#bug-discovery" class="anchor"></a>Bug-discovery</h2>
<p>One thing that I've found tremendously useful is narrowing down bugs. Armed with a repro, setting Claude off to track down issues has been a wonderful time saver. Additionally, asking it to explain the issue in detail with links to the source is very handy indeed. It's not, however, able to discover <i>all</i> bugs, even with a lot of time. When working on the fix for a <a href="https://github.com/ocaml/odoc/pull/1400">particularly nasty bug</a>, I found that with the patch applied we'd get a different error somewhere deep in some of Jane Street's async ecosystem. I had a good suspicion of what the problem was given the changes that had been made already, as the code I had altered had an analogue elsewhere in the codebase that hadn't been fixed, so I thought this would be quite a good test for Claude. I gave it lots of hints, but it flailed at the problem for several hours, often giving up, sometimes blaming the OxCaml compiler, and sometimes upstream OCaml. In the end I couldn't get Claude to make useful progress so I implemented what I thought <a href="https://github.com/ocaml/odoc/pull/1400/changes/3164566c010cd110b283643cdf18cbb9ab3400c4">should be the fix</a> and indeed the problem went away. So there are clearly classes of bugs that are still beyond Claude's capabilities to understand, which isn't an unexpected result.</p>
<h2><a href="https://jon.recoil.org/atom.xml#api-boundaries" class="anchor"></a>API boundaries</h2>
<p>I've found it very helpful to have API boundaries to help structure the code that Claude has been producing. Anil has long been enthusiastically pushing the idea that we should write the <code>mli</code> files first, which constrain what types and values are available between the modules. We can then write tests that target these interfaces, and then adjust them where the tests have shown them to be inelegant or downright unusable. We can then write the implementations and watch the tests start to pass. A particularly interesting example of this is the odoc plugin interface. The experience of writing several very different plugins that all extended odoc in different directions was very helpful, and I adjusted the interface quite a few times. I also adjusted the <a href="https://jon.recoil.org/reference/odoc/extensions.html" title="extensions">documentation</a>, where qualities about how the interface <i>behaved</i> that weren't obvious from the types could be carefully noted, for example how scripts might be made to behave correctly when the odoc pages were in an SPA shell. Far too often in the OCaml community we've relied just on types and modules as documentation for our libraries, and this is rarely enough.</p>
<h2><a href="https://jon.recoil.org/atom.xml#failure-modes" class="anchor"></a>Failure modes</h2>
<p>When I was working on the <a href="https://jon.recoil.org/2025/12/claude-and-dune.html" title="claude-and-dune">dune rules</a>, I made the mistake of going too long without giving Claude some architectural constraints, and I ended up with a Big Ball of Code that I then had to spend time unpicking and teasing apart into sensible looking modules. I had rather hopefully believed this to be a Claude Opus pre-4.5 problem, but I still hit this recently when adding a new feature, when it just added vast amounts of code to one file to implement it, and the code was all very unstructured and unsatisfactory. This was despite going through a design process where we went through the goals, the use cases and desired features, but crucially, not at the level of the code.</p>
<p>Another failure mode I observed was <i>my</i> failure. It's very easy, and very tempting, to get your agent to do the next neat thing on the roadmap. Especially when you've just spent a while going through the design and planning for the previous feature and Claude has got started on it. The problem is that this can generate a large amount of code that kind-of-works but has a bunch of bugs, which can end up costing a lot more time and effort. The cost of starting the agent going is much smaller than the cost of wading through the results, and it's quite easy to end up drowning under a load of very interesting and partly cool half results. I'm very much reminded of Dr Ian Malcolm's words from Jurassic Park: "your scientists were so preoccupied with whether or not they could, they didn't stop to think if they should."</p>
<h2><a href="https://jon.recoil.org/atom.xml#what's-next?" class="anchor"></a>What's next?</h2>
<p>In the more immediate future though, perhaps with my odoc-maintainer hat on, I still want to make sure that I extract the useful parts of what I've done and get them upstreamed. While everything I've done is all open source and published, there's a lot of work I need to do so that others in the community will benefit from my changes. While it's technically possible to add my opam-repo to your switch, and install my versions of odoc, dune, and my various plugins, I don't think many people are actually going to do that. Worse than that, people might get their agents to just grab the source and mutate it further, just diluting the efforts going into it.</p>
<p>Fortunately I've been talking with <a href="https://choum.net/panglesd/">Paul Elliot</a>, who has volunteered to shepherd the dune PR through to completion. I'll be working with him on this of course, but I'm hoping he'll be doing the lion's share of the work.</p>
<p>The OxCaml work will be taken on by <a href="https://github.com/art-w">art-w</a> who's already done an excellent job getting Luke Maurer's patches into shape and PR'd to ocaml/odoc.</p>
<p>We'll be having a forward-looking odoc meeting on the 8th April to think about the roadmap for odoc, and I'm confident that my work will help us in the discussions of what directions odoc will be heading in over the next year or so. Whilst the bigger picture of how the world is evolving plays out we need to at least carry on maintaining the community software, and use LLMs wisely and carefully as another tool in our toolbox to help us keep the code as useful and bug free as possible.</p>
